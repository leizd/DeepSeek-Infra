## P0：4.4.6 远程链路闭环

### Verified Spool 跨 Scheduler Attempt 复用

- 首次 Attempt 冻结 `BackupRunPlan`（policy/target/contributor/recipients/snapshot kind）。
- Executor 在 Snapshot 之前查找 `.backup-spool`；`runPlanDigest` 匹配则跳过重建与 Age 重加密。
- 同一 Slot 的重试继续原 ciphertext，而不是 mint 新 `backupId`。

### Remote Reconcile

- `reconcile_target_store`：Commit 后 Head 前滚、Receipt 重建、Catalog 回填、未提交 Transaction 孤儿标记。
- **绝不重新生成 Backup。**

### 可跨重启的 Remote Restore

```text
POST /api/workspace/restores/from-target   → restoreId, phase=fetching
POST /api/workspace/restores/{id}/fetch    → 幂等续传
```

- 同一 `restoreId` 在进程退出后继续；Remote ETag/VersionId 变化则拒绝。

### Governance 经 TargetSession

- Catalog / Pin / Retention 支持 filesystem 与 S3 store，不再强制 `require_root()`。

## Incremental foundation

- Merkle root over `(contributorId, path, size, sha256)`
- Coverage-safe tombstones：unavailable contributor 不产生 DELETE
- Adaptive full checkpoint 条件（depth/interval/delta ratio/index loss/recipient rotation…）
- Snapshot index（可重建，非信任根）
- Ancestor protection for pinned descendants
- Intra-delta payload reference dedupe（非 convergent encryption）

## 明确不做

- Convergent encryption / CDC chunking / 跨 Target 全局去重
- WebDAV GA / Incremental Safety Backup
- 改变 4.4.2–4.4.6 Full Backup 恢复兼容性

## 证据

`tests/test_backup_447_contracts.py` 钉住 spool 重试复用、remote reconcile、restore resume、incremental diff/Merkle/retention 祖先保护与 force-full 条件。

## 验收一句话

> 同一个失败的远程 Schedule Slot 必须继续使用原来已经验证过的 Age 密文；成功后，后续备份只上传相对于已提交父快照真正变化的数据，任意增量链都能从 Full Ancestor 确定性重建并通过 Merkle Root 验证。
