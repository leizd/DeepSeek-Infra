# 4.4.5 — Fenced Backup Commits & Replica Lineage

<!-- docs-language-switcher:end -->


中文标题：**租约围栏的备份提交与副本谱系**

4.4.4 搭起整套自动备份能力之后，4.4.5 把"长任务租约、目标侧提交、Catalog 并发、
Mirror 并发"闭合为真正的事务闭环：失去租约的 Worker 无论执行到哪一步，都不能发布、
编目或删除任何文件；一个 Schedule Slot 在目标上只能形成一个正式 Commit。

## 证据合同

- `tests/test_backup_fenced_commit_contracts.py` 把 4.4.5 验收面钉成 12 个 evidence key：一 Slot 一正式 Commit、过期租约拒绝状态迁移、目标 Writer Lease 围栏、崩溃对账后孤儿不可见、blocked-retryable / slot-conflict、Catalog 投影 CAS、目标回滚/分叉/克隆检测、Retention 快照 CAS、Mirror 不可变 Generation、Epoch/Sequence 围栏、Policy Recipient 变体隔离、客户端 Replica/Sequence 接受。

## 单标签页 Mirror 上传选举

- 多标签页通过 `localStorage` Leader Lease + `BroadcastChannel` 心跳选举唯一上传者：只有 Leader 收集完整前端 Envelope 并调用 `PUT .../backup-mirrors/{id}/frontend`，携带稳定的 `clientReplicaId` 与按 Profile 单调递增的 `clientSequence`（以及 `expectedHeadGenerationId` CAS）。
- Leader 关闭或租约过期后其他标签页接管并延续 Sequence；上传成功广播新的 `generationId`，同伴跳过重复上传；Restore Fence 期间冻结收集与上传，离线或 5xx 失败按指数退避重试。

## Mirror 按 Recipient Group 生成变体

- 不再把所有启用 Policy 的 Recipient 合并成一个集合：同一 Generation 按稳定的
  `recipientGroupId = sha256(sorted(recipients))` 为每个 Policy 的精确 Recipient Set 生成一个
  变体(`state.<groupA>.age` / `state.<groupB>.age`)——本地盘、离线盘与归档组合密钥互不获得
  对方的 Mirror 解密能力，也不再产生 `recipient-mismatch`。
- `mirror_status` 按 Generation 变体列表匹配 Policy 的 Recipient Set;`mirror_files` 与定时
  备份只读取为本 Policy 密封的那个变体（缺失即显式失败）；显式 `recipients=` 上传仍只生成
  单一变体。

## 服务端 Mirror Epoch 与 Sequence 围栏

- 服务端按 Profile 在 `HEAD.json` v2 内维护已接受状态(`acceptedEpoch`、`acceptedEpochIndex`、
  `acceptedSequence`、`epochIndexes`)，不再比较客户端时间：被取代的 Epoch 即使携带更晚的
  客户端时间也以 `mirror-stale-epoch` 拒绝；`clientSequence` 必须按 Profile 单调递增
  (`mirror-stale-sequence`)——包括 Restore 之后的新 Epoch 接管。
- `acknowledgedAt` 仅作新鲜度展示字段，不参与并发排序；相同 Epoch + Envelope + Recipient
  的重放保持幂等；旧版 Mirror 接受首个 v2 上传的任意 Sequence 后才启用围栏。

## Mirror 改为不可变 Generation

- 每次上传产生一个不可变 Generation(`generations/<generationId>/state.<recipientSetDigest>.age`
  + `metadata.json`，含代际谱系、Client Replica/Sequence 与 Recipient Variant)，完整解密
  往返验证并 fsync 之后，才以 CAS 更新 `HEAD.json` 指针；读取端一次解析 HEAD 并从同一
  不可变 Generation 复制文件——密文与元数据永远属于同一代。
- 读取路径重新核对密文与 Generation 描述的 Digest；上传可携带 `expectedHeadGenerationId`
  做 `mirror-head-conflict` CAS；相同 Envelope Digest 但 Epoch 不同不再被当作幂等；崩溃
  上传留下未被引用的 Generation，由下一次上传修剪（保留 HEAD 与其父代）。
- 4.4.4 旧版 Mirror 经回退路径保持可读，直到首个新 Generation 将其取代。

## Retention 快照 CAS 与 Trash Journal

- Retention Preview 携带 `retentionRunId`、`targetGeneration`、`catalogHeadHash` 与
  `policyDigest`;Apply 时发现 Catalog Head / Target Generation / Retention Policy 任一变化
  或 Preview 不完整，即以 `retention-stale-snapshot` 拒绝并要求重算；每次移动前断言
  Writer Lease 仍然有效。
- `minimumHealthyCopies` 的健康副本必须同时满足：对象存在、Receipt 字节与 Slot Marker
  的 Receipt Digest 匹配、Commit Marker 有效、Age Header 可读、最近 Scrub 成功或刚完成
  创建验证——损坏或未提交的文件不再计入健康数。
- Trash 移动走四阶段 Journal(`intent → payload-moved → receipt-moved →
  event-committed`)，中断事务在下一次 Apply/Finalize 被确定性前滚完成，`.trash` 里永远
  不会留下半个备份。

## 目标回滚、分叉与克隆检测

- 目标 Marker 升级为 v2：携带 `incarnationId`、`ownerInstallationId` 与实时 Commit Head
  (`targetGeneration` / `latestCommitHash`)，每次 Slot 提交后原子推进；
  `.backup-targets/<targetId>.checkpoint.json` 记录本安装最近一次可信状态。
- Generation 回退 → `target-rollback-detected`；同 Generation 但 Head 不同或 Incarnation
  改变 → `target-fork-detected`；同一 Target ID 同时存在于两个挂载位置 →
  `target-clone-detected`。异常解决前禁止发布与 Retention，只读列出与 Scrub 保持可用；
  用户可显式选择"采用此分支"(`POST .../adopt`）或"注册为新目标"(`POST .../register-new`)。
- 单纯换盘符的磁盘在旧位置消失后可正常重注册；4.4.4 时代的 v1 Marker 在首次写接触时
  就地升级，Generation 与 Head 从磁盘上的 Commit 推导。

## Catalog 成为目标事务的投影

- Catalog 不再决定哪个备份存在——Commit Marker 与 Receipt 才是权威。每个治理事件
  （Receipt、Pin、Scrub、Unlock 演练、Trash、Restore、Delete）先以不可变事件文件落入
  `events/<prefix>/<entryHash>.json`（携带 `previousEntryHash`、Target Generation 与
  写者 Fencing Token),JSONL Catalog 只是可由事件重建的索引。
- 追加接受 `CatalogPrecondition`(Head Hash + Target Generation 快照）：绑定旧快照的写入
  以 `catalog-head-cas-failed` / `catalog-generation-cas-failed` 失败，并发写者经目标
  Writer Lease 串行化，Hash Chain 永不分叉。
- 重建回放不可变事件 + 遗留 JSONL + 磁盘 Receipt,Pin/Scrub/Unlock/Trash 历史不再丢失；
  分叉事件被确定性跳过并计数。
- `frontend_index_path()` 改为随 `STATIC_DIR` 动态解析，消除对本地前端构建产物存在性的
  隐性依赖。

## Scheduler 状态机修复

- `blocked` 拆分为 `blocked-retryable`（携带 `nextRetryAt` 与 `blockedReason`）与
  `blocked-terminal`（尝试耗尽或超出 Catch-up Window)；目标盘重新上线后 Blocked Run
  自动被重新认领；接管不完整目标事务的 Run 以 `reconciling` 显式呈现。
- 同一 Schedule Slot 被其他 Run 正式提交后，落败的 Run 进入 `superseded`（终态，Slot
  保持 Complete)，不再无限重试。
- 手动 Run 改用 `manual/<uuid>` Slot Key 并校验 Slot 插入确实成功——同一秒内的两个请求
  不会再创建重复 Run。
- Worker 循环不再静默吞异常：Tick 失败写入结构化日志并累计连续失败计数。

## 发布崩溃恢复

- Worker 启动时按确定性规则对账每个目标：Commit Marker 幸存而 Scheduler Run 仍活跃 → 校验后收敛为 `complete`；Receipt 缺失 → 从事务 Journal 精确重建；Catalog 投影缺失 → 仅从已提交 Receipt 重建；Object 存在而 Commit 不存在 → 保持不可见，Grace Period 后连同未发布 Receipt 移入 `.orphaned/`。
- 绝不通过重新运行整个备份来恢复——同一 Schedule Slot 不会产生第二份密文。
- Catalog 存在无 Slot Commit 的记录时标记 `catalog-corrupt`，Retention 在对账完成前拒绝 Apply 与 Finalize，分叉或半写的 Catalog 永远无法驱动删除。

## 目标侧 Writer Lease

- SQLite Run Lease 只保护本机调度库；每个目标新增 `.target-lock/writer.json` 单写者租约：`O_EXCL` 原子获取，仅在过期且持更高 Fencing Token 时才可被抢占。
- Commit Marker 发布、Catalog 追加、Pin/Unpin、Scrub 记录、Retention 移动、Trash 恢复与 Catalog 重建全部被 Writer Lease 覆盖；Run 心跳同时续期目标租约，Executor 每次 Checkpoint 同时断言两者——失去目标所有权的 Worker 在下一次文件移动前停止。
- API 侧的 Pin、Scrub、解锁演练与 Retention 操作使用新分配的 Fencing Token 获取同一租约，与后台备份互斥；不能可靠提供原子创建/原子 Rename 语义的文件系统被明确标记为 `unsupported-atomic-target`，绝不假装等同于本地磁盘。

## 不可变对象与 Slot Commit Marker

- Backup Object 上传完成不再等于备份存在：密文按内容寻址存入
  `objects/sha256/<prefix>/<digest>.age`（跨 Slot 去重），意图先写入
  `transactions/<runId>.json` Journal，Receipt 以 `receipts/<backupId>.json` 不可变
  落地，最后才以 `O_EXCL` 创建 `commits/<policyId>/<slotHash>.json` Commit Marker——
  携带 Run 的 Fencing Token 与全目标递增的 Generation/Hash 链。
- 同一 `(policyId, scheduleSlot)` 的第二个发布者：Object Digest 相同则收敛到已有
  Commit（并补齐缺失的 Catalog 投影）；不同则以 `slot-commit-conflict` 拒绝，旧
  Fencing Token 会被明确命名。崩溃或失去租约的 Worker 最多留下不可见的孤儿对象与
  Receipt，绝不会形成第二个正式备份。
- Retention、Scrub、解锁演练与 Catalog 完整性检查统一经 Commit 感知的候选链解析
  密文；4.4.4 旧目标的 `backups/<filename>` 布局仍可读取、校验与清理；被多个 Receipt
  共享的内容寻址对象在仍有存活引用时不会被移入 Trash。

## 主动续租的 Run Lease Guard

- 每个执行中的 Run 持有 `RunLeaseGuard`：租约 300 秒，心跳每 60 秒续租一次；
  首次续租失败立即设置 Run 级 Cancel Event。
- Contributor Snapshot、Age 加密与验证、目标复制、目标端 SHA-256、Catalog 追加与
  Retention 移动都在分块边界执行 Checkpoint；Lease 丢失后禁止进入任何可见提交步骤。
- 所有租约断言使用真实当前时间，不再复用 Run 启动时冻结的时间戳。

## 过期租约拒绝一切状态迁移

- `complete_run`、`record_run_phase`、`requeue_run` 与 `fail_run` 在校验 Owner 与
  Fencing Token 之外，同时拒绝已过期的 Lease；Lease 续期拒绝 Terminal Run。
- 执行中途租约过期并被新 Worker 接管后，旧 Worker 无法发布、编目、清理或完成；
  该 Run 记为 Abandoned 等待回收，同一 Schedule Slot 最终只有一个正式结果。

## 不包含

- 不做 S3、WebDAV 或其他云目标；不做增量、去重与分卷；不托管 Recovery Identity；
  不保存 Passphrase；不自动恢复或重放任务；既有前端 Bundle 预算不提高。
