- Status: Approved

- Baseline: `origin/main` at `288442d1` (PR #128 merged, `VERSION=4.4.15`)
- Target: `4.5.0`

## Assumptions

1. 4.5.0 is a multi-slice production milestone, not a single oversized commit.
2. The existing remote restore `restoreId` becomes the durable Recovery Job identity; a second Job ID and a second state store are not introduced.
3. Existing restore routes remain compatible. New job-control and DR routes are additive.
4. The default verified ciphertext-cache quota is 20 GiB and remains explicitly configurable; no adaptive quota heuristic is added.
5. Recovery holds keep the existing six-hour protection window and renew at most every 30 minutes while protected work remains active.
6. Local unit/contract tests are necessary but not sufficient for release. Real MinIO, real Age, subprocess restart, and fault-injection Evidence must run before any related check is marked PASS.

## Objective

Freeze the 4.4.14/4.4.15 backup wire formats and turn the selective object-set restore path into an operable disaster-recovery data plane. A recovery must be preflightable, bounded, parallel, resumable per ciphertext component, cache-aware, lease-protected, pausable, safely abortable, auditable, and capable of completing an isolated recovery drill without mutating the live Workspace.

The primary user is an operator restoring a large production Workspace from an S3-compatible target under network failures, process restarts, disk pressure, and long-running federated commit workflows.

## Frozen compatibility contract

The following are release invariants, not migration targets:

- `storageProtocol=object-set-v1` remains unchanged.
- Receipt v4 and Commit Marker v4 remain unchanged.
- Every Control and Payload Component continues to use independent randomized Age encryption.
- Public object identity remains ciphertext SHA-256 plus ciphertext size.
- Whole-Age v2-v5 restore compatibility remains permanent.
- Projection semantics, selection digests, Output/Support separation, full logical Merkle verification, safety backup, and federated transaction semantics remain intact.

No 4.5.0 implementation may introduce object-set-v2, Receipt v5, Commit v5, deterministic/convergent Age, plaintext-derived remote keys, plaintext-hash cloud CAS, cross-Backup/Policy/Target deduplication, historical Component references, or random-access Age ciphertext.

## Audited 4.4.15 baseline

The Foundation Slice is present on `origin/main`, but the production milestone is not:

| Area | Current 4.4.15 behavior | 4.5.0 requirement |
|---|---|---|
| Scheduler | Worker and byte budgets are enforced; tasks are submitted in input order; `priority` and `maxOpenFiles` are unused. | Honor stable priority and an independent FD semaphore. |
| Filesystem publish | Object-set Components use the Scheduler. | Preserve behavior and frozen commitments. |
| ObjectStore/S3 publish | `_publish_object_set_via_store` uploads Components serially and performs full readback hashing. | Bounded parallel upload; authoritative checksum when proven, otherwise full readback. |
| Restore creation | `_object_set_member` calls `stat` for every object in every Receipt before Projection is known. | Verify Receipt/Commit locally, stat/fetch Controls, then stat only the required closure. |
| Payload fetch | `_fetch_object_set_components` advances one `componentFetchIndex` serially. | Parallel per-component durable states with arbitrary completion order. |
| Preview/materialize | Preview writes a report, but materialize calls `_plan_object_set_projection` and decrypts Controls again. | Persist and strongly bind a reusable verified plan; no Control redecode on a valid hit. |
| Materialize pipeline | All required Components download before sequential decrypt/verify/extract. Plaintext ZIPs survive through the layer loop. | Overlap network and crypto stages and scrub each plaintext ZIP immediately after verified extraction. |
| Recovery holds | Fixed six-hour `expiresAt`; no renewal generation or heartbeat. | Renewable leases retained for active, paused, prepared, committing, and recovery-required jobs. |
| Adaptive delta | A monolithic temporary candidate ZIP is created before object-set Components are recompressed. | Prepared Object Set supplies exact cost and is encrypted directly. |
| DR control plane | API calls are individually durable, but there is no single pause/resume/preflight/readiness/drill model. | Existing restore session becomes a durable Recovery Job orchestrator. |

## Architecture

### One durable Recovery Job

The remote restore session is upgraded additively. Its canonical identity remains `restoreId` and its durable record remains under `.restore-staging/<restoreId>/session.json`. Existing readers must tolerate the additive fields.

```json
{
  "restoreId": "restore_x",
  "targetId": "prod-s3",
  "backupId": "I8",
  "selectionDigest": "sha256...",
  "chainDigest": "sha256...",
  "phase": "fetching-components",
  "pauseRequested": false,
  "abortRequested": false,
  "resources": {
    "networkWorkers": 4,
    "cryptoWorkers": 2,
    "maxInFlightBytes": 268435456,
    "maxOpenFiles": 64
  },
  "progress": {
    "requiredComponents": 18,
    "cachedComponents": 7,
    "verifiedComponents": 11,
    "downloadedBytes": 734003200
  }
}
```

State transitions are compare-before-write and idempotent. Only one durable record is authoritative; API responses are projections of that record.

```text
created -> preflighted -> fetching-controls -> controls-verified
        -> projection-frozen -> checking-cache -> fetching-components
        -> components-ready -> materializing -> verified -> safety-backup
        -> preparing -> prepared -> committing -> complete

side states: paused, aborting, failed, recovery-required
```

`pauseRequested` and `abortRequested` are durable intents, not thread interruption. A pause stops admitting new Component work, lets an in-flight chunk reach a journal checkpoint, and then enters `paused`. Resume validates partial length/digest state before continuing. Abort semantics are phase-dependent:

- Before federated prepare: scrub scratch/plaintext, unpin cache entries, release holds.
- Prepared but not committed: abort the staged transaction, then clean up and release protection.
- Any partial commit or uncertain participant state: enter `recovery-required`; do not release holds or cache pins.

### Transport scheduler

The Component Scheduler owns three independent resources:

- Worker semaphore: simultaneous transfer tasks.
- Byte semaphore: aggregate transport working set, not full Component sizes.
- FD semaphore: file descriptors reserved by a task.

Tasks are admitted in stable ascending priority order, retaining input order within the same priority:

- `0`: Control objects.
- `1`: parent/support dependencies.
- `2`: selected outputs.
- `3`: speculative prefetch; 4.5.0 defines the class but does not enable speculative fetching by default.

The same scheduler semantics apply to filesystem publish, ObjectStore publish, Control fetch, and Payload fetch. Completion order must not alter ObjectSetDigest, Receipt, Commit, Projection, or materialized bytes.

### Lazy object validation

Restore creation validates immutable Receipt bytes, Receipt digest, Commit v4, `objectSetDigest`, inventory shapes, and the Control's membership without performing a HEAD for every Payload. It then performs HEAD/GET only for Controls. After authenticated Control decryption and Projection closure, it performs HEAD/GET only for required Payload Components.

Projection recoverability and whole-snapshot health are deliberately separate:

```json
{
  "projectionRecoverable": true,
  "snapshotHealth": "last-scrub-ok"
}
```

The most recent complete Scrub or Recovery Drill supplies whole-snapshot health. A selective recovery never claims that unselected objects were revalidated.

### Per-component durable transfer state

`componentFetchIndex` is migrated on read and no longer written for object-set jobs. Each required ciphertext digest has independent state:

```json
{
  "componentStates": {
    "<ciphertextDigest>": {
      "state": "partial",
      "downloadedBytes": 25165824,
      "expectedBytes": 67112431,
      "remoteETag": "opaque",
      "remoteVersionId": "opaque",
      "priority": 1
    }
  }
}
```

Allowed states are `queued`, `downloading`, `partial`, `verified`, and `failed`. `verified` requires exact ciphertext size and SHA-256. A process restart may resume a partial only when its recorded source identity and local length still match; otherwise the partial is scrubbed and fetched from offset zero.

### Verified encrypted Component cache

The cache is a performance layer under `.backup-component-cache/sha256/<prefix>/<ciphertextDigest>.age`. It is never a trust root and contains no Project, Path, Contributor, selection, secret, or plaintext identity.

Cache hit requirements:

1. Filename digest is canonical SHA-256.
2. Exact ciphertext size matches the authenticated Control/Receipt commitment.
3. Streaming SHA-256 of the cached ciphertext matches the digest.

Misses download to `.<digest>.partial`, stream and hash, flush/fsync, and atomically rename. A corrupt entry is deleted and refetched. Active and `recovery-required` jobs pin required entries. Quota GC is LRU over verified, unpinned entries only; default quota is 20 GiB. Cache corruption may increase network traffic but cannot change restore correctness.

### Verified Projection Plan

Preview persists `.restore-staging/<restoreId>/verified-plan.json`. The plan contains no secret and is strongly bound to:

- `selectionDigest`.
- Ordered chain `objectSetDigest` values and their derived `chainDigest`.
- Ordered Control ciphertext digests.
- `plannerSchemaVersion`.
- Required Component digests, roles/priorities, expected ciphertext bytes, and existing projection report.

Materialize reuses the plan only when every binding matches the durable session. A mismatch fails closed into explicit replanning and replaces the plan atomically; it never silently reuses stale output. Valid plan reuse must not decrypt or decode Controls again.

### Network/crypto pipeline and plaintext lifetime

Network workers place verified ciphertext paths onto a bounded crypto queue. Crypto workers decrypt, verify the plaintext ZIP commitment, safely extract expected paths, fsync the extracted content where required, and scrub the plaintext ZIP immediately. Ciphertext remains available in the cache/scratch store; plaintext archives do not wait for all Components.

No secret is persisted in the job record, verified plan, cache metadata, logs, metrics, or Evidence. Existing temporary Secret Slot semantics remain the only secret handoff.

### Renewable recovery-hold leases

Each hold is replaceable using its current ETag/version and contains:

```json
{
  "restoreId": "restore_x",
  "leaseGeneration": 7,
  "lastRenewedAt": "...",
  "expiresAt": "...",
  "state": "active"
}
```

Renewal extends `expiresAt` to now plus six hours and increments `leaseGeneration`. A job renews no more frequently than every 30 minutes during `created`, preflight/fetch/materialize phases, `paused`, `safety-backup`, `preparing`, `prepared`, `committing`, and `recovery-required`. Terminal `complete`, clean `aborted`/`rolled-back`, and failure proven to precede any transaction release holds. Renewal conflicts fail closed: the job stops destructive progress and reports protection degradation rather than assuming it is safe.

### Prepared Object Set

Incremental staging produces a `PreparedObjectSet` of plaintext component ZIPs plus a Control draft. Exact prepared bytes drive Adaptive Full. Under threshold, those ZIPs are encrypted directly; over threshold, they are scrubbed and the frozen run plan resolves to Full. Component creation may stop as soon as accumulated exact prepared bytes cross the threshold. The existing monolithic temporary candidate ZIP is not built for object-set-v1.

Prepared plaintext is always local scratch, short-lived, excluded from backups, and scrubbed on success, fallback, cancellation, and process-recovery cleanup.

### Provider integrity modes

`TargetCapabilities` gains an explicit bounded value:

- `strong-provider-checksum`: the provider returns an authoritative full-object SHA-256 that equals the expected ciphertext digest.
- `full-readback`: current streaming GET and SHA-256 verification.

The mode is selected only by a capability probe that proves response checksum semantics for single-part and multipart objects. User configuration, ordinary ETag, multipart ETag, or checksum request support alone is insufficient. Any missing, weak, or inconsistent checksum falls back to full readback.

### Recovery preflight

Preflight is read-only and runs after the verified plan exists but before mutation. It reports chain length, selected logical bytes, required/total/cache-hit Component counts, remote bytes, scratch/safety-backup/free disk bytes, target health, projection recoverability, last whole-snapshot health, and blocking reasons.

Disk need includes materialized tree, safety backup estimate, non-cached ciphertext, bounded crypto plaintext, and configured reserve. Insufficient capacity returns a stable conflict error before federated prepare. Preflight estimates never delete cache entries or mutate the live Workspace.

### DR readiness and Recovery Drill

`GET /api/workspace/disaster-recovery/status` reports the latest formally committed recoverable point, latest successful Scrub, latest successful isolated Drill, target/index/cache health, actual `rpoSeconds`, and an explicitly estimated RTO derived from recent successful recovery stage throughputs. RTO is never labelled or treated as an SLA.

A manual Recovery Drill uses the same Recovery Job engine through fetch, decrypt, Merkle verification, and materialization, but selects an isolated drill root and never runs the live federated commit. It verifies contributors, scrubs the drill root and plaintext, releases holds/pins, and persists an auditable result. Automatic weekly scheduling is deferred to 4.5.1.

## Additive API contract

Existing endpoints remain valid. The following are added:

| Method | Path | Contract |
|---|---|---|
| `POST` | `/api/workspace/restores/{restoreId}/preflight` | Build/reuse the verified plan and return read-only capacity/dependency/health results. |
| `POST` | `/api/workspace/restores/{restoreId}/pause` | Persist pause intent; idempotently return current job state. |
| `POST` | `/api/workspace/restores/{restoreId}/resume` | Clear pause intent after validating resumable state; idempotently continue. |
| `GET` | `/api/workspace/disaster-recovery/status` | Return bounded-cardinality readiness, RPO, and estimated RTO fields. |
| `POST` | `/api/workspace/disaster-recovery/drills` | Create a manual isolated Recovery Drill. |
| `GET` | `/api/workspace/disaster-recovery/drills/{restoreId}` | Read the durable drill result/job state. |

All request bodies are authenticated and boundary-validated. Errors preserve the existing `AppError` shape and use stable machine codes. New response fields are additive camelCase fields. No endpoint returns secrets, plaintext paths outside local operator context, or provider credentials.

## Observability contract

On-call must be able to answer:

1. Which phase is a Recovery Job in, and why did it stop?
2. Are transfers bounded, making progress, hitting cache, retrying, or failing integrity checks?
3. Are holds healthy and renewing for every protected job?
4. What are current recoverability, RPO, and recent measured stage throughputs?

Signals use stable event names and `restoreId` correlation. Metrics use only bounded labels such as phase, direction, result, target kind, and integrity mode; never backup IDs, digests, paths, Project/Contributor names, credentials, or error messages as labels. Required counters/histograms include transferred bytes/components, cache hits/misses/corruptions, transfer duration, crypto duration, materialization duration, pause/abort outcome, and hold-renewal outcome.

## Threat model and safety boundaries

Trust boundaries are remote Receipt/Commit/ObjectStore responses, cached ciphertext, partial files, persisted session/plan JSON, API inputs, provider checksum claims, and recovered archives.

- Tampering: every ciphertext source is verified against authenticated/committed size and SHA-256; plaintext ZIP commitments and safe extraction remain mandatory.
- Information disclosure: cache and telemetry contain ciphertext identity only; no secrets or logical metadata escape Control encryption.
- Denial of service: worker/byte/FD/queue/disk/cache quotas are hard bounds; untrusted size fields are range-checked before allocation or filesystem work.
- Repudiation: job transitions, pause/abort requests, renewal failures, and drill outcomes are durable and correlated by `restoreId`.
- Elevation/path escape: archive path validation and isolated drill roots remain mandatory; drill code has no live-commit capability.

## Code style

Follow the repository's typed Python 3.10 conventions and stable JSON naming at public/durable boundaries:

```python
@dataclass(frozen=True, slots=True)
class ComponentState:
    digest: str
    expected_bytes: int
    downloaded_bytes: int = 0
    state: Literal["queued", "downloading", "partial", "verified", "failed"] = "queued"

    def as_dict(self) -> dict[str, Any]:
        return {
            "state": self.state,
            "expectedBytes": self.expected_bytes,
            "downloadedBytes": self.downloaded_bytes,
        }
```

Use `AppError` with stable codes at boundaries, atomic JSON writes for job state, deterministic sorting for commitments/plans, streaming I/O for Components, and explicit bytearray scrubbing for secrets.

## Testing strategy

- Small unit tests: scheduler admission, component-state migration, cache validation/eviction, plan binding, lease transitions, capacity arithmetic, readiness/RTO aggregation.
- Medium integration tests: Memory/Filesystem TargetStore parallelism, restart recovery, corrupt partial/cache entries, pause/resume/abort phase contracts, isolated drill root, API validation/error shapes.
- Large E2E tests: real S3-compatible MinIO, real Age helper, cold/warm cache, subprocess exit/resume, fault injection, long-running hold renewal, and federated recovery-required behavior.
- Compatibility tests: frozen protocol constants and byte-stable object-set/Receipt/Commit fixtures plus legacy Whole-Age restore.
- Coverage: repository-wide Python coverage remains at least 95%; no skipped/disabled tests are accepted as release Evidence.

## Gates and success criteria

### Gate A — Transport

- Remote ObjectStore Component upload and selective download actually overlap.
- Worker, byte, and FD maxima are observable and never exceeded.
- Priority is honored without starving already-admitted work.
- Per-component resume survives process exit and arbitrary completion order.
- Restore creation performs zero HEAD/GET for unselected Payload Components.

### Gate B — Cache

- Verified warm-cache recovery performs zero remote Payload GET.
- Corrupt cache entries are rejected, removed, and refetched.
- Active/paused/recovery-required pins prevent eviction; quota never evicts pinned entries.

### Gate C — Pipeline

- Valid Preview plans are reused; Controls are not redecrypted/redecoded during materialize.
- Network and crypto work overlap within independent bounds.
- Plaintext Component ZIPs are scrubbed immediately after verified extraction and on every error path.

### Gate D — Safety

- Long-running, paused, prepared, committing, and recovery-required jobs renew holds.
- Terminal safe outcomes release holds and pins.
- Preflight rejects insufficient disk before mutation.
- Pause, resume, and phase-aware abort remain correct across process exits.

### Gate E — Cost and provider integrity

- Prepared Object Set eliminates object-set double compression.
- Oversized delta creation stops before Age encryption.
- Proven provider SHA-256 avoids full readback; weak/missing claims fall back.
- Ordinary and multipart ETags are never accepted as SHA-256.

### Gate F — DR

- Preflight exposes accurate closure/cache/disk/health estimates.
- Readiness reports actual RPO and explicitly estimated RTO.
- Manual Recovery Drill uses the production recovery engine, never mutates live Workspace, and leaves no plaintext drill tree.

### Gate G — Evidence

- Real MinIO cold selective recovery passes.
- Real MinIO warm-cache recovery passes with zero Payload GET.
- Real subprocess pause/resume and per-component resume pass.
- Fault injection covers cache corruption, remote mutation, disk exhaustion, lease conflict, and partial federated commit.
- `object-set-v1`, Receipt v4, Commit v4, randomized Age, and legacy restore compatibility all pass frozen-contract checks.

## Boundaries

- Always: fail closed on integrity/protection uncertainty; preserve unrelated worktree content; isolate runtime paths in tests; scrub secrets/plaintext; run focused tests before full gates; record only real Evidence.
- Ask first: new third-party dependencies, authentication changes, CI provider/credential changes, cache default above 20 GiB, or any public breaking change.
- Never: change frozen wire formats, trust ETags, make cache authoritative, log secrets/logical metadata, mutate live Workspace during drills, automatically replay active paid work, or claim CI-only checks passed without artifacts.

## Deferred beyond 4.5.0

- Polished recovery UI before Gates A-D are green.
- Automatic weekly Recovery Drill scheduling (target 4.5.1).
- Adaptive/AI cache sizing.
- Privacy padding or speculative prefetch enabled by default.
- Any new wire format, encryption construction, remote deduplication protocol, or cross-snapshot Component reference.
