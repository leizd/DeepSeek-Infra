## Overview

Version 4.9.1 tracks the Rust Storage and Transfer Plane cutover across 13 data and security domains.
The cutover is still in progress: Python remains the production storage authority until every phase below
has provider-backed evidence. The current native slices implement strict `object-set-v1`, Receipt v4,
Commit v4, signed replica-attestation verification, and the exact sovereign federation transfer journal
with SQLite durability and transactional CAS. Rust now also independently recomputes the complete
`predictive-planning-proof-v1` security binding instead of accepting declared PASS values. These slices
and the autonomous storage Evidence validator now recompute Receipt/Commit provider bytes and bindings.
The Rust proof plane also verifies the complete signed `federated-dr-proof-v1` recovery-capability,
production-restore, cleanup, and immutable-failure semantics, plus bilateral Fleet trust, signer rotation,
signed readiness, and challenge replay semantics. These slices do not yet move payload bytes, execute a
restore, or authorize remote effects. Rust now also reproduces the legacy recovery/process Evidence
validators without treating their static parity corpus as provider execution evidence.

- Python and Rust accept the same frozen valid `predictive-planning-proof-v1` document and return the exact same ordered errors for all 69 v8 mutation vectors.
- Rust recomputes the source risk, fresh-state components, observation set, forecast, backtests/calibration, price catalog, candidate safety, what-if state, and outer proof digests.
- Every one of the 24 promoted/core predictive Evidence checks routes through the typed validator; unsupported checks remain fail closed.

- Rust fmt, full-workspace Clippy with warnings denied, full-workspace tests, Python oracle tests, ruff, mypy, and the native runtime contract gate pass locally.

This remains development evidence. It does not assert real Three-MinIO execution, production
storage ownership, or exact-head release readiness.

The recovery/process Evidence validator slice is locally verified on 2026-09-05:

- Python and Rust return the same ordered errors for all 61 v13 cases covering restore digest/phase, post-recovery Receipt binding, PID separation, non-clean termination, boot epoch increase, three normalized endpoint identities, unbounded decimal inputs, and the legacy non-empty evidence boundary.
- An additional 38 parsed-document cases cover JSON integer precision, nested object insertion order, Python string/repr conversion, Unicode decimal digits and casefolding, and the reference interpreter's 4300-digit conversion limit. Decimal comparisons allocate at most 4300 normalized digits. A 400-digit nonzero computed digest remains truthy and cannot bypass the receipt-binding comparison.
- Evidence parsing enables the existing serde JSON integer-precision and insertion-order features. Cryptographic canonicalizers continue sorting their own copies; the pre-existing frozen digest and signature corpora verify that this changes no wire commitment.
- All 16 existing check names route to their specific validator; unsupported checks remain fail closed.
- The frozen corpus explicitly identifies itself as validator parity only. The Rust module cannot run a restore, contact MinIO, inspect a process, or authorize a provider effect.
- The permissive 4.8.0 behavior for an unknown but non-empty legacy schema remains isolated and documented for compatibility; changing it requires a separately versioned contract rather than a silent migration drift.

This is not real Three-MinIO recovery evidence and does not transfer storage or recovery authority
from Python to Rust.
